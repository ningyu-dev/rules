# 宁雨 · 规范规则库

把给排水规范条文转成可计算、可校验、可追溯的结构化数据。

**这个仓库不包含任何计算代码。** 它是纯数据 + 校验脚本，依赖方向永远是单向的：`core` 消费 `rules`，`rules` 不反向依赖任何代码。一旦规则库开始 import 计算逻辑，就失去了独立验证规则本身正确性的能力。

## 规范原文获取

**PDF 就放在本仓库工作区的 `archive/<标准号>/` 下，但不进 git**（`.gitignore` 的 `archive/**/*.pdf`）。

为什么不入库：一本规范动辄几十 MB，全放进去每次 clone 都很重，而规则库本身只有几百 KB；且一旦推上去，从 git 移除要重写历史。
为什么不放仓库外：放在 `archive/<标准号>/` 里，路径与标准号一一对应，脚本和人都好找。

仓库内提交的是**可校验的证据**：

| 文件 | 作用 |
|---|---|
| `archive/<标准>/<标准>.pdf` | 规范正文。**本地文件，git 忽略** |
| `archive/<标准>/SOURCE.md` | 下载 URL、**来源类型**、公告号、实施日期、SHA-256 |
| `archive/<标准>/SHA256.txt` | PDF 的 SHA-256 |
| `archive/<标准>/announcement.html` | 住建部公告原文（体积小，供强条清单机械比对） |
| `archive/<标准>/announcement.sha256` | 公告原文的 SHA-256 |

获取与校验：

```bash
# 下载并归档（会自动写 SHA256.txt 与 SOURCE.md）
python scripts/archive_pdf.py GB50345-2012 <PDF_URL> --type 官方

# 人工下载的，从本地文件归档
python scripts/archive_pdf.py GB50345-2012 --from-local ~/Downloads/xxx.pdf --type 官方

# 校验手上这份是不是核对时那一份
python scripts/archive_pdf.py GB50345-2012 --check

# 公告原文批量归档（按登记表里的 evidence 链接）
python scripts/archive_announcements.py --apply
```

**文件可信由哈希保证，而非由二进制入库保证。**

### `来源类型` 这一栏必须当真

| 取值 | 含义 | 能否作为条文出处 |
|---|---|---|
| `官方` | 住建部门户网站发布件，或正式出版文本 | 可以 |
| `转载` | 地方政府网站等转载的同一份文本 | **不可以**，只能定位与交叉比对 |

把转载件当官方件记，等于把「来源未经真实性验证却声称已核对」重演一遍。要转为可用，须取得官方件后重新归档并把该字段改为 `官方`。

### GB 50015-2019 的 PDF 是扫描件

179 页，`/Font` = 0，无文字层。条文与附录 F 的公式**无法用脚本提取**，逐条核对只能人工读原页。

`provenance` 因此分两个字段：`page_pdf`（图像页序）与 `page_printed`（规范印刷页码）。扫描时丢失了页面标签，两者不一定一致，以 `page_printed` 为准。

## 信源：标准会不会变，靠什么知道

`docs/信源与更新机制.md` + `sources/standards.json` + `scripts/check_sources.py`。

登记表覆盖给排水全行业 **14 个门类、109 本标准与文件**，其中 27 本属本产品范围，库里 79 条规则全部落在范围内；已废止的 8 本单列黑名单。**全景与范围是两个字段**（`group` 与 `in_scope`），不做区分会让规则库无限膨胀。

判据层面记住四件事：

1. **四查，不是三查**——公告、措辞、日期、形态。前三查**查不出修改单**，必须加第四查：查标准号后有无 `/XG`
2. **"废止《XXX》"与"废止……相关强制性条文"处置完全不同**：前者整部不得再引，后者标准照引、所列条号不得再作强条
3. **母子关系双依据同引**：不一致处以通规为准，一致部分母标准继续有效
4. **征求意见稿不是依据**，只能用来预判换版

```bash
python scripts/check_sources.py              # 分类汇总 + 核对到期 + 库内标准是否都登记了
python scripts/check_sources.py --unverified # 名称/编号未核的条目（此状态不得录条文）
```


## 为什么不用 RAG

RAG 回答「天沟坡度要求多少」的方式是检索一段原文丢给人。在设计场景这不可用，原因有两点：

1. **校验需要的是可比较的值，不是一段文字。** 判断坡度是否达标需要 `0.005` 这个数，不是「不应小于百分之零点五」这句话。
2. **RAG 输出不可复现。** 同一问题两次检索结果可能不同，而设计文件必须能追责。

RAG 在本项目中的定位降级为：辅助工程师查阅规范原文，**不参与任何计算和判断**。

## 三条硬约束

### 一、版本主键必须是「标准号 + 年份 + 条文号」

规范会换版。GB 50015 从 2003 换到 2019，GB 50014 从 2006 换到 2021。

注意区分**废止**与**修订**。两件事要分开说，因为证据强度不同：

- **GB 50015-2019 共 30 条强条**，公告 2019 年第 171 号逐条列号，**已核原文**。第 5 章（雨水）**0 条**——所以 5.2 节里大量「应」字条文不是强条，需要单独一个等级档去承载。
- 这 30 条的**强条属性已自 2022-04-01 起全部废止**，依据是 GB 55020-2021 公告**附件 2**（已取到官方 `.docx` 并逐条解析，存于 `archive/GB55020-2021/废止强条清单.docx`）。附件所列 30 条与公告 171 号所列 30 条**逐项相同**——一条不多、一条不少，故该标准**无残留强条**。
- 两者都属「废止」而非「修订」，**不改变条文数值**。

清单已结构化为 `sources/abolished_strong_clauses.json`（9 项 / 78 条，由 `scripts/build_abolished_list.py` 从官方附件生成，条号不经人手），并由 `scripts/check_strong_clause.py` 在每次校验时比对库内条目的强制等级——**「引用已废止的强条」这类肉眼读不出的缺陷，现在能自动发现**。


系统必须能回答两个问题：

- 用户手上这份图纸，设计时依据的是哪一版？
- 这一版和上一版相比，阈值变了没有？

因此 `rule_id` 的格式由 schema 的正则强制：`^GB\d{5}-\d{4}-(...)$`。不能只用标准名组织条目。

### 二、条文与条文说明必须物理隔离

GB 50015 全文版是「规范正文 + 条文说明」混排的。**条文说明是给编制人员看的解释性内容，设计文件中引用不得。**

`content_type` 字段区分三种内容：

| 值 | 含义 | 能否参与校验 |
|---|---|---|
| `clause` | 规范正文 | 可以 |
| `explanation` | 条文说明 | **禁止** |
| `table` | 附录表格 | 可以 |

这是最容易犯、且一犯就会被工程师当场发现的错误。

### 三、附录表格要表达成可计算的表

GB 50015 附录 F 是屋面溢流设施泄流量计算，附录 G 是重力流系统立管最大设计排水流量。这些是查询表。

结构化之后它不只用来查表，更自动成为校核依据 —— 算出结果立刻能比对附录 G，超了就直接报出超了多少。

## 强制等级

`mandatory_level` 四级，务必区分：

| 值 | 含义 | 处理方式 |
|---|---|---|
| `strong_clause` | 规范强条 | 必须拦截，不允许用户绕过 |
| `mandatory_general_code` | 强制性通用规范强条 | 必须拦截 |
| `recommended` | 推荐性条文 | 告警，用户可确认后继续 |
| `reference` | 参考值（设计手册取值等） | 仅提示 |
