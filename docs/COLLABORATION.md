# 协作纪律

## 仓库归属与提交身份

**所有成员共享同一个 git 身份（`suninx`），因此 git log 无法区分谁改了什么。**

两位成员已多次报告「工作区存在第三方修改，建议确认来源」，并误将主理人的修复归属为未知第三方。这是身份共用导致的必然歧义，不是异常。

## 规则

### 1. 修复必须可复现，不采信自述

成员声称「已修复 X」时，**必须独立验证**，且优先写脚本而不是手工改数据。

真实案例：
- 成员声称已加 `mandatory_level_pending` 与 `safety_critical` 字段并阻断 50 条 → 实测两个字段一条都不存在，36 条仍为 `recommended`
- 主理人用脚本 `tag_blocking.py` 独立处理，不依赖成员自述

涉及安全属性的改动（强制性等级、阈值、阻断标记），一律用可重跑脚本执行并留下输出。

### 2. 修改他人未提交改动前必须先核对

若工作区存在非本任务产生的改动，先 `git diff` 确认内容与来源，再决定如何处理。不得擅自覆盖或丢弃。

### 3. commit message 必须写明作者与依据

格式：

```
<改动摘要>

作者：<主理人 / 成员名>（修订前一项时注明）
依据：<复核意见 / 规范条文 / 独立验证结果>
```

### 4. 不猜测工作区改动来源

无法确定时直接说明「无法确定来源」，不要猜成第三方。共用身份下这个信息不存在。

### 5. 冲突以内容为准

两个成员对同一问题给出不同结论时，**以文件实际内容为准**，不是以最后写入的为准。实测优先于自述。

## 已验证的协作教训

| 教训 | 代价 |
|---|---|
| 未采信自述，直接信任成员声称的修复 | 溢流设施「应设置」曾长时间标为 `recommended`，用户可确认跳过 |
| 报「通过，0 条」而不区分成因 | 草稿看起来合规，实际全部被过滤 |
| 拆分条目以迁就 schema | 5 张表把行标签当列轴，5.2.38 丢失「塑料110」维度 |
| 把规范条文当数值来源（主理人失误） | 技术方案 7 项数据与现行规范冲突 |
| 过度保守的版权判断（主理人失误） | 工作区无原文，17 项数值三轮无法核对 |
| 用 `set()` 做覆盖比对 | 清单 6 条 EP 重复，同骗过两名成员 |
| 写了功能重复的校验脚本（主理人失误） | 两个结论来源，事后不知跑的是哪个 |

## 核心方法论：校验 ≠ 正确

**规则库的可靠性不能靠「跑通校验」证明，只能靠「逐条人工核对 + 留痕」保证。**

校验脚本的作用是**防止已知错误复现**，不是**发现未知错误**。

依据：本项目已发生的六次失败，**没有一次能被现有校验自动发现**——

| # | 形态 | 层级 | 现有工具能发现吗 |
|---|---|---|---|
| 1 | 附录 G 数值错位 | 数据层 | 否 |
| 2 | 5.2.38 静默丢维度 | 数据层 | 否 |
| 3 | 强条清单 29/31 | 数据层 | 否 |
| 4 | 校验脚本回退自证循环 | 校验层 | 否 |
| 5 | 清单 EP 重复 + `set()` 校验 | 校验层 | 否 |
| 6 | 「46 条」口径不明 | 数据层 | 否 |

六次全部靠**人工交叉复核**或**成员自陈**暴露。

根本原因是：**校验的覆盖范围远小于问题的发生范围。** 校验能查「格式对不对、数量等不等」，查不出「这个数字对不对、这个分类依据是什么」。前者是形式正确性，后者是语义正确性。

因此：

- 校验通过**不构成**数据正确的证据，只能说明「已知的坑没再踩」
- `page`、`verified_by` 全为 0/null 时，校验必然通过——**这是设计如此，不是缺陷**
- 任何汇总数字（条数、覆盖率、工时）都要写明口径，否则会成为下一个「来源不明的数字」
- 断言式校验必须做**反向注入测试**：注入已知错误，确认脚本会报，才算有效。已做的三次：`tag_blocking`（36 条）、`verify_checklist`（EP 重复）、`fetch_mandatory_clauses`（断网回退）
