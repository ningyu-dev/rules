# 协作纪律

## 仓库归属与提交身份

**所有成员共享同一个 git 身份（`suninx`），因此 git log 无法区分谁改了什么。**

两位成员已多次报告「工作区存在第三方修改，建议确认来源」，并误将主理人的修复归属为未知第三方。这是身份共用导致的必然歧义，不是异常。

## 规则

### 1. 修复必须可复现，不采信自述

成员声称「已修复 X」时，**必须独立验证**，且优先写脚本而不是手工改数据。

真实案例：
- 成员声称已加 `mandatory_level_pending` 与 `safety_critical` 字段并阻断 50 条 → 实测两个字段一条都不存在，36 条仍为 `recommended`
- 主理人用脚本 `tag_blocking.py` 独立处理，不依赖成员自述

涉及安全属性的改动（强制性等级、阈值、阻断标记），一律用可重跑脚本执行并留下输出。

### 2. 修改他人未提交改动前必须先核对

若工作区存在非本任务产生的改动，先 `git diff` 确认内容与来源，再决定如何处理。不得擅自覆盖或丢弃。

### 3. commit message 必须写明作者与依据

格式：

```
<改动摘要>

作者：<主理人 / 成员名>（修订前一项时注明）
依据：<复核意见 / 规范条文 / 独立验证结果>
```

### 4. 不猜测工作区改动来源

无法确定时直接说明「无法确定来源」，不要猜成第三方。共用身份下这个信息不存在。

### 5. 冲突以内容为准

两个成员对同一问题给出不同结论时，**以文件实际内容为准**，不是以最后写入的为准。实测优先于自述。

### 6. 只推 main，禁止 `git push --all`

本地可能存在 `backup/*` 分支（历史重写前的回退点）。这些分支里可能有**不宜公开的过程文档**——它们被 `.gitignore` 挡在正常提交之外，但 `git push --all` 会把分支连同历史一起推上去，等于绕过忽略规则。

```bash
git push origin main      # 正确
git push --all            # 禁止
```

`backup/*` 分支一律不设上游（`upstream` 为空），这样普通 `git push` 不会带上它。判断方法：

```bash
git for-each-ref --format="%(refname:short) upstream=%(upstream:short)" refs/heads
```

只要 `backup/*` 的 `upstream` 是空的，它就只存在于本地。

## 核心方法论：校验 ≠ 正确

**规则库的可靠性不能靠「跑通校验」证明，只能靠「逐条人工核对 + 留痕」保证。**

校验脚本的作用是**防止已知错误复现**，不是**发现未知错误**。

依据：本项目已发生的七次失败，**没有一次能被现有校验自动发现**——

| # | 形态 | 层级 | 现有工具能发现吗 |
|---|---|---|---|
| 1 | 附录 G 数值错位 | 数据层 | 否 |
| 2 | 5.2.38 静默丢维度 | 数据层 | 否 |
| 3 | 强条清单 29/31 | 数据层 | 否 |
| 4 | 校验脚本回退自证循环 | 校验层 | 否 |
| 5 | 清单 EP 重复 + `set()` 校验 | 校验层 | 否 |
| 6 | 「46 条」口径不明 | 数据层 | 否 |
| 7 | **反向注入本身失效** | **校验层** | 否 |

七次全部靠**人工交叉复核**或**成员自陈**暴露。

根本原因是：**校验的覆盖范围远小于问题的发生范围。** 校验能查「格式对不对、数量等不等」（形式正确性），查不出「这个数字对不对、这个分类依据是什么」（语义正确性）。

### 第 7 轮：反向注入本身会失效

两位成员先后踩中同一次失败。成员重做第 5 轮反向注入时，**第一次报了「通过，85 行」**；复核随后做同样的注入，**第一次也失败了**（`lines.index('### P3')` 抛 `ValueError`，实际标题含全角空格，精确匹配失败，什么都没插入）。

第 4 轮是校验手段失效，**第 7 轮更隐蔽：校验手段被正确执行了，但被测对象没有被正确污染**。两者表面结果完全一样（都是「通过」），但防范手段不同：

| 轮次 | 特征 | 能否靠看退出码防范 |
|---|---|---|
| 第 4 轮 | 校验手段**没在校验** | 能（退出码也不对） |
| 第 7 轮 | 校验手段**正确执行，但被测对象没被污染** | **不能**（退出码确实是 0） |

因此反向测试必须自带**「注入已生效」的断言**（比较注入前后的文件指纹），而不是靠测试者记得确认。

已固化为 `scripts/selftest_injection.py`，四步闭环：干净 0 → 注入生效 → 污染 1 → 还原 0。它用文件指纹而非出现次数验证注入，因此与被测对象写法无关，不会因写法不同而失效。

### 由此推出的纪律

- 校验通过**不构成**数据正确的证据
- `page`、`verified_by` 全为 0/null 时校验必然通过——**这是设计如此，不是缺陷**
- 任何汇总数字都要写明口径，见 `DESIGN.md` D-009。判据：**第一个问题不是「N 对不对」，而是「N 是怎么数出来的」**
- 断言式校验必须做反向注入测试，且**必须确认注入本身生效**（D-010）
- 做注入测试时用临时目录，**不要往被 glob 匹配的位置放临时文件**。曾因在 `docs/` 放下 `临时核对清单.md` 导致 glob 匹配到两个文件——虽然脚本正确拒绝了，但这是不该制造的状态

### 已做反向注入验证的校验

| 脚本 | 注入内容 | 结果 |
|---|---|---|
| `tag_blocking.py` | 36 条强制模态词降级 | 全部标记 |
| `verify_checklist.py` | EP 条目重复 | 3 项断言，退出码 1 |
| `fetch_mandatory_clauses.py` | 断网回退 | 退出码 2（未验证） |
| `selftest_injection.py` | 注入有效性自检 | 四步闭环全绿 |

复核额外测了 glob 的两个边界，均正确：多文件匹配时报错退出；清单改名为「屋面雨水核对清单.md」后仍能匹配。
