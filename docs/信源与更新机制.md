# 信源与更新机制

**这份文件回答一个问题**：半年后规则库要更新，第一步该去哪里、看什么、看到什么算变了。
登记表在 `sources/standards.json`，检查脚本是 `scripts/check_sources.py`。

**这张表由脚本生成**，不手工维护：

```bash

```

## 一、为什么单独做一层

规则库现在的 85 条，`verified_by` 全为 null，`page` 全为 0。也就是说**没有一条是核对过的**。
但真正的问题不在这里——真正的问题是：**没人知道下次该去哪核对，也不知道核对什么算通过。**

缺这一层会导致三种固定失败：

| 现象 | 后果 |
|---|---|
| 只存了 PDF，没存公告 | 标准被废止了，库里还是「现行」，且无从发现 |
| 只记了标准号，没记版本形态 | 修改单（`/XG`）改的正是数值，标准号没变，检索不到 |
| 把转载站当出处 | 排版与原文有差、可能混入 OCR 错误，条文一旦引错就退回 |

所以信源层的产物不是链接清单，而是**判据**：去哪看、看哪一句、哪一句说明什么。

## 二、四查（不是三查）

对每一本标准，逐项走完才算核对过。**前三查查不出修改单，也查不出局部修订**——这是本项目最容易漏的一环。

| 序 | 查什么 | 具体动作 | 判据 |
|---|---|---|---|
| 1 | **公告** | 打开住建部「标准公告」栏目，用**标准号**站内检索；再看栏目里按日期倒序翻近两年 | 有无针对该标准的发布 / 局部修订 / 废止公告。**一条都没有 ≠ 现行**，只说明还没查到 |
| 2 | **措辞** | 进入公告正文页，逐字读第一段 | 见 §三。四个句式对应四种处置，一字之差处理完全不同 |
| 3 | **日期** | 同一页的「实施日期」字段 + 正文末尾的成文日期 | 发布日、实施日、有无过渡期。**审查基准是勘察设计合同签订日，不是今天** |
| 4 | **形态** | 看公告标题有无「局部修订」；看标准号后缀有无 `/XG`；下载公告附件看废止清单 | **号、名、年版三者全不变而内容已改**——只有这一查能发现 |

### 为什么三查不够

前三条查的是「这本书还在不在、叫什么、什么时候生效」。它们查不出**书还是那本书、内容已经换了**：

| 形态 | 标准号 | 名称 | 年版 | 条文内容 | 三查能否发现 |
|---|---|---|---|---|---|
| 换版（50015-2003 → 2019） | 变 | 变 | 变 | 变 | 能 |
| 整部废止 | 不变 | 不变 | 不变 | 失效 | 能（有公告） |
| 强条属性废止 | 不变 | 不变 | 不变 | 部分条不再作强条 | 能（公告逐条列号） |
| **修改单 `/XG`** | **不变** | **不变** | **不变** | **改数值** | **不能** |
| **局部修订** | **不变** | **不变** | **不变** | **改所列条文** | **不能** |

后两行是本项目的盲区。实例：**GB 18918-2002 出了 `/XG2-2025`**。按前三条查，它依然是「2002 年版、现行、2003-07-01 实施」，看不出任何变化；而排放限值已经变了。

**处置**：凡见到 `/XG`，或公告标题带「局部修订」字样，一律视为**内容已变更**，按新数值重核该标准下全部条目，并在 `provenance` 里注明依据的是修改单后的版本。

### 一条容易反过来的判据

「没查到公告」不等于「标准现行」。它只等于「这次没查到」。所以 `check_sources.py` 里 `last_checked` 为空时一律记「从未核对」，不允许记成「现行」——**未核对是一个状态，不是一个结论。**

## 三、公告措辞判据（可直接照用）

| 措辞 | 含义 | 处置 |
|---|---|---|
| 「废止现行国家标准**《XXX》**」（书名号后不接「相关强制性条文」） | **整部废止** | 该标准任何条文不得再引，规则库对应条目须整批下线 |
| 「废止……**相关强制性条文**」＋逐条列号 | **部分废止** | **标准本体现行**，所列条号不得再作强条引；规则条目保留，`mandatory_level` 降级并标注 |
| 「现批准……自 X 年 X 月 X 日起实施」＋「现行工程建设标准相关强制性条文同时废止」 | **新通规发布** | 母标准与通规须**双依据同引**：不一致处以通规为准，一致部分母标准继续有效 |
| 「局部修订的条文……自 X 年 X 月 X 日起实施」 | **局部修订** | 只改所列条文，其余照旧；须逐条比对是否命中本库条目 |

**一句话里两种都有就拆开分别判。** GB 55038-2025 的公告即此形态。

### 两个必须记住的实例

- **GB 50788-2012**：被 GB 55026/55027 整部废止 → 任何场合不得再引。
- **GB 50014-2021 §5.15.3**：强条属性被 GB 55027-2022 废止 → 标准照引，该条不得再作强条引。**这两者处置完全不同，混淆即事故。**

## 四、频率

| 触发 | 动作 |
|---|---|
| **每季度一次**（1/4/7/10 月首周） | 跑 `check_sources.py`，把超期条目逐本走完四查，更新 `last_checked` |
| **项目开工前** | 对涉及的标准走一遍四查。审查基准是合同签订日，不是今天 |
| **见到「征求意见稿」** | **记录但不采信。** 征求意见稿不是依据，正式稿发布后才有约束力 |
| **见到 `/XG`** | 立即查，属高优先；修改单改的通常正是数值 |
| **规则库新增条目** | 该条所属标准必须在 `sources/standards.json` 里有登记，否则不得入库 |

### 反例（本行业真实流传的错误信息）

- **「GB 14554-2019」不存在。** 现行仍是 GB 14554-1993，2018 年征求意见稿至今未发布正式版。见到有人引 2019 版，说明来源不可靠。
- **CJJ/T 243-2016 现行。** 住建部 2026-01-23 才发布修订**征求意见稿**，反馈截止 2026-02-27。征求意见稿不得作为设计依据。

## 五、`last_checked` 的写法

```
last_checked: "2026-10-22"
checked_by:   "沈澄 给排水工程师"
```

**只写「已核对」不写日期，视为未核对。** 这是 D-009 的直接应用：结论不能脱离口径，
「核对过」必须能回答「什么时候、对哪个版本的哪一句」。

`checked_by` 记**角色而非仅姓名**——角色决定这次核对是否在资质范围内。

## 六、状态词的四个取值

登记表用四个词描述一本书的状态，**不许混用**：

| 取值 | 含义 | 能否引用条文 |
|---|---|---|
| `current` | 已核到公告，确认现行 | 可以（仍须核对条文原文） |
| `presumed` | 按常识判断现行，**未核公告** | 可以引号，但引数值前必须核 |
| `pending_verify` | 状态本身存疑（可能已换版或废止） | **不可以**，先核 |
| `abolished` | 已确认废止 | 绝对不可以 |

`name_verified: false` 是另一条独立的轴：**标准名称或编号本身还没被官方确认**。此状态下只能保留占位，**不得录入任何条文**——名称错则条文全错。当前 8 本处于此状态，用 `--unverified` 可列出：

```bash
python scripts/check_sources.py --unverified
```

## 七、与规则库的接口

三层关系，方向单向：

```
sources/standards.json        信源与现行性登记（本标准活着的证据）
        ↓
rules/building_rain/*.json    条文与数值（rule_id + provenance）
        ↓
core（尚不存在）              计算与校验
```

- `standards[].entries_in_library` 记录该标准在库里的条目数，用于一眼看出「登记了但没录」。
  当前 17 本登记中，**11 本为 0 条**——这不是遗漏清单，是范围边界，须逐本决定「录还是明确不录」。
- 每条规则 `provenance.page` 必须能落回登记表中某个 `sources` 渠道。
  落不回去的条目，说明它的出处不在可控信源内，**不得进入生产库**。

## 八、原文归档约定

PDF 放工作区、**不进 git**；公告与哈希进 git。

```
archive/<标准号>/
  <标准号>.pdf            ← 正文，.gitignore 忽略
  SOURCE.md               ← URL、来源类型、公告号、实施日期、SHA-256
  SHA256.txt              ← PDF 哈希
  announcement.html       ← 公告原文（十几 KB，可机械比对强条清单）
  announcement.sha256
```

```bash
python scripts/archive_announcements.py --apply        # 公告批量归档
python scripts/archive_pdf.py GB50345-2012 <URL> --type 官方
python scripts/archive_pdf.py GB50345-2012 --check     # 校验手上这份是否同一份
```

**`来源类型` 只有「官方」能作条文出处。** 「转载」（地方政府网站等）可读、可定位、可交叉比对，但不得作为 `provenance` 的最终依据。这一栏不是备注，是判据——把转载记成官方，就是第 4 轮失败的翻版。

### 每条记录必须答全六个问题

少一个，下一个人就无法复核：

| 问题 | 字段 | 缺了会怎样 |
|---|---|---|
| 从哪个页面下的 | **来源页面** | 只知直链，入口不可复核；链接失效就找不回来 |
| 直链是什么 | PDF 直链 | 无法重新下载 |
| 谁、什么时候下的 | 下载人 / 下载时间 | 无法追责，也无法判断是否过期 |
| 怎么下的 | 下载方式 | 分不清「脚本抓的」与「浏览器点的」，复现方式不同 |
| 是官方还是转载 | **来源类型** | 可能把转载件当出处 |
| 是不是全文 | **完整性**（页数） | 可能把节选当全文用 |

```bash
python scripts/audit_archive.py     # 本地台账：有 PDF 的必须记全哈希与来源；本地无的不算缺陷
```

**台账不接受「已知问题白名单」**——白名单是「绿着但坏了」的开端。有问题就红。

**SOURCE.md 只记出处，不记本地有没有 PDF。** PDF 不进 git，本地有无是每台机器各自的运行时状态：写进版本库必然过期，还会让下一个人把「文档说没有」当成结论。**没有就按出处去取，而不是在文档里记一笔「未下载」。** 本地状态由 `audit_archive.py` 在运行时判断。

**重建工作区会丢掉全部 PDF**（它们被 gitignore）。换机器或重新 clone 后，先跑 `audit_archive.py` 看一眼，别把「目录存在」当成「正文在」。


**公告页不覆盖重下**：页面改版会改变哈希，重下会把「页面改版」误记成「公告变了」。要重下须显式删旧文件。
