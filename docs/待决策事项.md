## P0-1 · PDF 是否入库（**已决策：放工作区，不入 git**）

| 项 | 内容 |
|---|---|
| **决策** | PDF **放在仓库工作区** `archive/<标准号>/<标准号>.pdf`，由 `.gitignore` 排除；**不进 git** |
| **入库的只有证据** | `SOURCE.md`（URL、来源类型、公告号）、`SHA256.txt`、`announcement.html`、`announcement.sha256` |
| **决策人** | 用户（2026-10-23） |
| **落地状态** | 已落地：`.gitignore` 改为 `archive/**/*.pdf` 通配；`scripts/archive_pdf.py` 负责下载/校验/写 SOURCE.md |

**为什么这么定**：核对必须读原文，每次都要去网站下载不现实；但一本规范动辄几十 MB，全入库会让 clone 变重、且从 git 移除需重写历史。折中点是**正文留本地、哈希进仓库**——文件可信由哈希保证，不由二进制入库保证。

**代价**：新克隆的人手上没有 PDF，需按 `SOURCE.md` 的 URL 下载后跑 `archive_pdf.py <id> --check` 比对哈希。这条已写进 README。

**一条必须守住的边界**：`SOURCE.md` 里有 `来源类型` 字段，只有「官方」（住建部门户网站发布件或正式出版文本）才能作为条文出处。「转载」（地方政府网站等）只能用于定位与交叉比对——**把转载件当官方件记，就是第 4 轮「来源未经真实性验证却声称已核对」的重演**。

**为什么不把 PDF 放仓库外**：放仓库内 `archive/` 下，路径与标准号一一对应，脚本与人工都好找；放仓库外就没有「这份 PDF 属于哪本标准」的结构性约束。

## P1-1 · 是否引入 OCR / PDF 工具链

**题面**：`archive/GB50015-2019/GB50015-2019.pdf` 是 179 页扫描件（`/Font` = 0），环境无任何 PDF/OCR 工具（实测未安装 `PyMuPDF`/`pdfplumber`/`pypdf`/`pdftotext`/`tesseract`）。

**主理人建议：不引入。** 理由：

1. **附录 F 的五个公式在官方原文里就是图片**，OCR 也读不出代数式
2. **OCR 误识不报错**（`8.30` → `3.30`），与本项目八次失败同型——数字看着有、但错了、没有检查会报
3. 引入后只能省下"找页码"的功夫，价值有限，却要承担误识风险

**若引入**：建议仅用于定位页码，数值与条文原文仍须人工比对。

**排期影响**：不引入 → 85 条全部按人工工时估。**不要按"迭代两三轮"估。**

**待确认**：GB 55020-2021、GB 55030-2022、GB 50345-2012、GB 51022-2015、GB 50014-2021、CJ/T 245-2021 六本标准原文**尚未下载**，其核对同样受此决策影响。

## P1-3 · 是否加 `source_authenticity` 字段

**成员第六轮建议，第七轮已验证其价值。**

**理由**：`provenance` 现有字段（page / source_text / extracted_by / verified_by）记录的是**「条文被谁读过、读自哪一页」**，但**表达不了「来源本身是否被证明为真」**。

这两件事是正交的：

- 一条抄自某在线数据库的条文，可以是 `extracted_by: manual`
- 一条抄自官方 PDF 的条文，也可以是 `extracted_by: manual`

**没有字段能区分二者。** 而第 4 轮的失败正是"来源未经真实性验证却声称已与官方核对"。

建议取值：`verified`（来源已与官方渠道比对）/ `unverified`（未比对）。
